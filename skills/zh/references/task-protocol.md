# Local Task Protocol

Use an existing suitable local record location in the project; otherwise use `docs/tasks/T-YYYYMMDD-NNN/README.md`. Verify ID uniqueness at the registration location. Slice IDs within a parent task are `S01`, `S02`. Lightweight requests need no record. The task entry point is the sole authority for overall identity, revision, status, phase, delivery target, and authoritative sources. `plan.md` is the sole authority for slice identity, revision, status, dependencies, executor, and detail links. Detail files contain only objectives, scope, sources, checks, and outputs. Make specifications, plans, checks, and recovery material reachable from the entry point.

Use YAML frontmatter for metadata. Task fields are `schema_version: 1`, `kind: task`, `id`, `revision`, `status`, `phase`, `delivery_target`, and nullable `plan`. A multi-slice plan uses `kind: plan`, `task_ref`, and `items`; each item has `id`, `revision`, `status`, `depends_on`, `assignee`, and `detail`. Detail files use `kind: slice`, `plan_ref`, and `slice_id`. Use only these status values: 待处理, 执行中, 待验收, 已完成, 阻塞, 已暂停, 已取消, 已取代. Record phase and delivery target separately; finishing the steps does not substitute for acceptance.

The task body records objectives and allowed write scope, effective sources and versions, completion criteria and actual check entry points, authorization and budget, workspace, unresolved conditions, output and evidence entry points, and next steps. Dependencies, the executor, and actual artifacts must be accessible for each task execution unit. Field templates are in `../assets/templates/`.

Increment the requirements revision of an affected task or slice when its objective, scope, applicable decisions, or completion criteria change. Progress and executor changes do not increment it. Dispatch and return records pin the task and slice IDs, dispatch ID, requirements revisions and source versions actually used, workspace, allowed write scope, and output and evidence locations. An executor's completion claim is only a return. The coordinator records an acceptance decision after checking the current sources, actual outputs, required checks, and dependencies. Evaluate reusable parts of returns from earlier revisions first; those returns must not overwrite progress on a newer revision.

The pending frontier includes only slices whose dependencies have been accepted, whose sources remain valid, and whose execution conditions are satisfied. Check integration and the overall delivery target even after all slices are complete. An independent review task may be `已完成` while the reviewed output has not passed. Record each acceptance item as 通过, 失败, 未执行, or 不适用, and bind its evidence to the content under test. Separate run material according to `.harness/runs/<task-id>/<run-id>/scratch|results|evidence/<executor>/`. Only the coordinator updates overall records, in the main task workspace.

When checking records or evidence, resolve `scripts/harness.py` from the installed location of this `zh` skill (beside this reference's parent directory). Run it with a Python 3.11+ interpreter that has the dependencies in `<installed-zh>/scripts/requirements.txt`; a separate tool virtual environment keeps those dependencies outside the business project. If no such interpreter is available, prepare one with `python3 -m venv <tool-venv>` and `<tool-venv>/bin/python -m pip install -r <installed-zh>/scripts/requirements.txt`. From the project working directory, invoke `<tool-venv>/bin/python <installed-zh>/scripts/harness.py validate --task <project-task-README.md> --format json`. Git must be installed and available on `PATH` for workspace version checks, including projects without Git metadata. Read the script's `--help` for scope, verification, and return metadata when creating those records. This tool does not replace business acceptance.
