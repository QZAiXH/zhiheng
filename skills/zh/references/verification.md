# Evidence, Review, and Acceptance

First identify the actual test entry point and subject under test for each completion criterion. Record behavior, structure, data, and environment separately. Independent review produces findings with precise locations along two axes: Standards (project conventions and code quality) and Spec (effective specification and scope). Review conclusions do not replace acceptance. Record each acceptance item as 通过, 失败, 未执行, or 不适用, with its supporting basis. Delivery of the review task itself and acceptance of the reviewed output are separate conclusions.

Bind evidence to requirements revisions and sources, files under test and their dependency scope, check rules and tool versions, test data, environment, execution method, actual output, and original location. Cover relevant uncommitted and untracked files in addition to Git HEAD; without Git, retain a file manifest and SHA-256 hashes. Verify the actual environment version separately for runtime state. Use `snapshot` to generate a manifest of the declared scope and `compare` to identify changes and items that cannot be verified. After a change, reuse only evidence that still applies and rerun affected checks.

For a new critical check, first verify in isolated examples that it rejects a deliberately invalid result, then that it accepts a valid result. When a required check fails or has not run, keep the corresponding work incomplete. First satisfy missing conditions within the authorized scope or use an equivalent entry point that meets the same requirement. Switch to diagnosis when failures repeat without a new hypothesis. In checkpoints and the task entry point, retain accessible locations for necessary evidence and the relationships needed for revalidation.
