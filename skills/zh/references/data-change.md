# Data Impact and Migrations

During onboarding, domain, and architecture stages, locate the databases, models, migration tools, history, existing data ownership, and retention requirements. During specification and planning, assess structure, constraints and indexes, existing data transformation or backfill, initial data, and persistence semantics individually. Assess business logic and the full version diff even when no migration file is added. Record whether there is an impact and the supporting basis; define completion criteria for migration, compatibility, rehearsal, and recovery separately.

During implementation, use the project's existing migration entry points and verify data retention, repeated runs, partial success, resumption, and coexistence of old and new application versions. During review, compare the actual models, code, scripts, and specification; use an isolated data rehearsal to check retained data and constraints. At release time, check the **full span** from the version deployed in the target environment to the candidate version, the target database's migration state, and its actual data. Specify whether the pipeline, startup process, or manual steps execute the migration to prevent duplicate execution by multiple parties.

Determine the order of migration, deployment, backfill, and contraction from the actual compatibility relationships. Verify migration state, retained data, business flows, and the running version before declaring a release successful. On failure, distinguish application rollback, forward repair, and data recovery, and proceed according to the batches already executed and the actual state. For tradeoffs involving irreversible deletion, downtime, or data loss, present the prepared options to the user for confirmation; continue routine operations within the confirmed scope.
