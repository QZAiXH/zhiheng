# Project Knowledge and Authoritative Sources

Obtain the facts needed for the current scope from existing `AGENTS.md`, project documentation, specifications, ADRs, code, and configuration. Distinguish verified current facts, target decisions confirmed by the user, research inferences, and outdated derived material; cite source versions or fingerprints. When information is incomplete, first identify gaps needed for the current work and investigate further as new scope is entered. For key business definitions, permissions and data ownership, core entity relationships, important module boundaries, and the primary technology stack, prepare reviewable options and their impacts for confirmation. Proceed autonomously with local implementation choices within the confirmed approach.

Within the authorized scope, write verified, reusable findings to the project's authoritative location and update conditional pointers from the task entry point. Keep temporary assumptions in run records. Maintain one authoritative source per fact. When a decision is superseded, record the supersession and reassess what depends on it.

For release tasks, use the project's existing pipelines and documentation to verify entry points for building, running, environments, configuration sources, migrations, verification, and recovery. If minimal instructions are missing, create a project entry point at `docs/workflows/release.md` and make it reachable from project knowledge navigation and the task entry point. Keep individual version and execution logs in the corresponding task. Determine the current environment state from actual observations.
