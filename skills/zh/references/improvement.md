# From Repeated Feedback to Skill Revisions

Skill maintenance tasks use the same local task protocol in the source repository. Keep original feedback in the project where the skill was used. For each occurrence, record the original request, expected and actual outcomes, skill version, environment, and evidence entry points in the maintenance task. Link similar observations under different conditions and nearby counterexamples. Distinguish causes related to project knowledge, instructions, tools, environment, and state. Verify commonality across tasks before deriving a minimal reproducible case; write project-specific facts back to project knowledge.

Store case inputs, independent observable criteria, sources, and applicability conditions in `tests/evals/`. Change the smallest failing part of the relevant `SKILL.md`, reference, or script. For discovery evaluations, provide only the request and candidate descriptions without forcing skill loading. For execution evaluations, give an independent executor the original request, skill, and necessary materials; keep expected outcomes on the evaluator side. Record actual artifacts, the version under test, tools and environment, the number of error corrections, duration, and cost where available.

Compare the previous and candidate versions using identical inputs and comparable conditions. Cover the original failure, representative variations, nearby false activations, and affected existing scenarios; add a no-skill control when assessing net value. Base quality fixes on actual results and efficiency gains on measurements. If the candidate regresses or evidence is insufficient, retain the existing effective version and record options for further revision, simplification, or retirement. When adopting a revision, record its version, sources, dependencies, cases, and rollback basis. Revalidate affected behavior when models, tools, dependencies, or new feedback change.
