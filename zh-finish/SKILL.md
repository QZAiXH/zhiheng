## 执衡 Harness v0.5（默认研发路径）

先读 [统一增强流程](../zh/references/harness-integration.md)。它把现有 zh 入口接到固定 goal-workflow 增强实现；以下步骤适用于本版研发任务，执行后返回，不与原版状态/知识写入并行运行。

使用增强 walkthrough/ship-it 与受控 deliver/reconcile/closeout。默认停 verified；真实 H/T/C/D、必要远端检查、授权交付及知识/任务交接全部核实后才能 completed。local 默认无 push、无 gh；github 需实际平台对账和 Issue 收尾。清理前确认所有执行停止、证据长期保留，不能删除未恢复分支或把已合入失败改写成未交付。

下文保留原协作经验和独立用法。若与增强合同的状态、知识、执行和交付机制冲突，以当前任务的增强合同为准；用户授权和项目规则始终优先，技能文本不会扩大权限。


# 收尾与本地交付

输入为本任务交付授权、目标/任务分支与 worktree、实际候选、独立验收及原始检查证据。计划阶段应已明确本地交付约定；从 `zh` 接收已约定本地交付时由主会话实际执行授权的提交、合并和清理，不重新索要相同授权。独立调用不扩展用户要求。适用项目规则若与自动合并约定真实冲突，先说明冲突并解决；不能自创“不得提交”限制，也不能绕过真实限制。自包含执行，不串联会改分支或重启确认的外部 Git 技能；用户显式要求其他技能时尊重该请求。

1. 读取 [任务记录](../zh/references/records.md)，核对实际 Git 状态、候选及 [zh-review](../zh-review/SKILL.md) 的独立结论。未通过或关键条件无法验证就保留现场，不能根据执行者自评交付。确认收尾是否已经部分完成。
2. 验收必须对应实际候选内容与基线。按授权只提交本任务内容；若审查针对未提交内容，证明提交树与已审内容相同，否则补相应审查。代码、测试、相关配置或环境变化后评估证据有效范围。
3. 检查目标分支最新状态。默认先在任务 worktree 整合最新目标，解决可确定的冲突，验证受影响行为并补必要独立审查，再向目标快进交付。项目约定其他合并方式则遵从。新的业务取舍交用户决策，失败保留现场。
4. 合并前再次核对目标版本和候选。目标再次变化就重新评估；目标工作区不适合合并的未保存变更会阻塞交付。不为绕过脏目标工作区或授权冲突，擅自用脚本回填、复制差异替代已约定的提交与合并；另有用户明确授权回填时按该范围处理。不通过别的 worktree 直接更新已检出的目标分支引用，不强推、重置或覆盖用户内容。
5. 在目标工作区执行已约定的本地合并，核对实际目标提交。执行必要整合检查；只有证据对实际候选和环境仍有效时才能复用，说明依据。提交相同不能代替环境相关运行验证。
6. 保存合并、验证结果及有用知识。仅把已验证、可复用的发现按项目既有入口持久化；大日志留在 Git 公共目录，任务记录清理后仍可恢复。保留旧 `.zhiheng/` 内容。
7. 按 [工作区规则](../zh/references/workspaces.md) 检查已跟踪、未跟踪及忽略内容，保存有用文件后仅清理本任务 worktree。禁止直接强制删除含未知内容的目录；任务分支默认保留，删除须有明确授权。

提交、检查记录和工作区一致性可使用 [Git 辅助工具](../zh/references/task-tools.md)，它不判断自然语言授权或语义验收。项目特殊合并策略超出工具支持时按上述规则使用原生 Git，并保留同等证据。

开发、独立验收、提交合并、整合验证和清理分别记录真实状态。验收失败、冲突、整合验证失败、清理失败分别记录原因及恢复路径；未完成约定交付不能报告全部完成，受阻时保留现场。恢复识别已完成阶段，不重复合并或错误清理。远端推送、PR 和发布只在已有明确授权范围内执行，不从本地合并推导权限。
