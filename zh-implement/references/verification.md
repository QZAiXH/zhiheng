# 按风险验证

验收条件先明确不等于所有测试代码必须先写。选择能发现实际问题的最小充分检查，优先复用已有测试、类型检查、构建及运行场景。项目必需检查仍要完成。

- Bug：优先获得可捕获用户原始症状的失败信号，修复后重跑同一场景；合适时保存回归测试。无法稳定复现时说明尝试与证据限制，不能宣称已捕获故障。
- 预期明确、边界复杂的逻辑：先写关键行为测试往往有益；TDD 是可选方法，不要求逐测试红绿循环。
- 普通功能：实现后补必要测试亦可；界面、文档和配置按风险选择视觉检查、链接/格式验证、真实命令或已有构建，避免为可逆小编辑堆测试。
- 前端页面与交互：按 [前端预览与验收](frontend-preview.md) 的浏览器方法核对正式候选；构建、截图及原型演示分别提供不同证据，不能据此单独认定真实交互已通过。
- 测试预期来自需求、契约、独立计算或可信示例。观察公开行为和真实调用边界，不镜像实现、不测试私有细节，不无依据修改断言求通过。
- 同一候选的有效检查可以复用。代码、测试、相关配置或运行环境改变后评估证据失效范围，只补受影响检查；通过后无新变化不反复全量测试。

记录命令、工作目录、环境、退出状态、输出及对应版本。未运行、已有失败、环境阻塞分别报告。比较策略成本时比较同等验收标准下的总时间、token 和返工，不仅首轮生成开销。机械通过仍需独立语义验收。
