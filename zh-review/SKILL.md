## 执衡 Harness v0.5（默认研发路径）

先读 [统一增强流程](../zh/references/harness-integration.md)。它把现有 zh 入口接到固定 goal-workflow 增强实现；以下步骤适用于本版研发任务，执行后返回，不与原版状态/知识写入并行运行。

使用增强 review-it 的真实独立上下文/受控审查入口核查完整 AC-ID、当前候选和原始工具证据。区分 Blocking/Warning/Info；零测试、意外跳过、缺报告、命令失败和未知结果不能判通过。修复轮数受限，耗尽进入 blocked；不能沿用本地检查来宣称 GitHub 远端验证完成。

下文保留原协作经验和独立用法。若与增强合同的状态、知识、执行和交付机制冲突，以当前任务的增强合同为准；用户授权和项目规则始终优先，技能文本不会扩大权限。


# 独立验收

本技能只审查并回传结论，不顺带实现、提交或合并。首次验收必须是真实新会话，不继承执行对话或执行者自评。调用者按 [委派规则](../zh/references/delegation.md) 启动独立审查；已经处于这样创建的审查会话时直接审查，不递归创建审查者。只复制完整执行历史的宿主不能宣称满足该要求；没有独立能力时报告验收受阻。

## 必要材料

- 用户确认的完整相关目标、范围、验收条件及变更决定，保留有意的业务取舍。
- 适用项目规范与来源；准确的基线、实际候选提交/内容和 worktree。
- 可自行读取的代码及 diff，包括相关新增文件；原始检查命令、退出状态、输出、环境与限制。
- 复杂任务的对话中已展示的整合计划、必要决定与执行角色记录；只需原始材料，不传完整执行聊天。

不要把“全部完成”“实现可靠”等自评、完整执行聊天或建议通过的结论当作前提。材料缺失就标出无法验证的具体条件，不用执行者断言补齐。先核对候选身份；有未提交或新增内容时明确包含范围，不能只看已提交 diff 而漏审。

前端任务按 [前端预览与验收](../zh-implement/references/frontend-preview.md) 读取已确认预览/设计依据、确认范围与待定事项、正式候选的浏览器操作证据。关键新交互缺少对应版本的实际预览确认时列为阻塞或无法验证；复用组件或通用弹窗不构成该业务交互的确认。核对主要流程和相关布局/状态，必要时在真实浏览器复查；模拟成功、截图或构建通过不能替代真实功能证据。材料缺失或环境受阻时标明无法验证，不把原型当成正式候选，也不自行替用户确认设计。

## 判断与回传

逐条件核实可观察行为，并分别判断需求符合度和项目规范；一个维度通过不能抵消另一个失败。复杂任务核对完整计划是否已展示、必要决定是否有依据、开发是否由执行会话完成；关键流程条件缺失或无法验证时如实报告，不由代码测试通过推定流程合规。检查附带范围变化，以及既有接口状态码、错误 reason、授权和行为契约是否被改变；不能仅凭测试通过或修改后的旧断言认定兼容。评估测试是否实际覆盖用户需求，必要时运行针对性检查。区分无关既有失败、本次回归和环境阻塞。规范判断引用真正适用的项目约定；一般设计偏好是建议，不凭空升级成硬性规定。

小任务一个独立会话覆盖所有维度。复杂任务确有需要才拆审查者，各自先独立判断再汇总；不默认双审查或固定跨模型。返工复查可保留本审查会话的条件、发现和原始证据，只接新候选及必要材料；范围实质改变或上下文混乱再新建。

输出：基线与候选身份；每个条件“通过／未通过／无法验证”及证据；发现分为阻塞、警告、信息；执行过的检查与限制。阻塞包括未满足条件和关键条件无法验证，不能给出总体通过。报告需要补充的最小证据或修复范围，避免无方向反馈。

交付使用的报告须绑定实际候选和检查覆盖。后续代码、测试、相关配置或目标分支变化，由 [zh-finish](../zh-finish/SKILL.md) 评估有效范围；不要机械重跑仍有效的整体验收，也不要沿用已失效的通过结果。
