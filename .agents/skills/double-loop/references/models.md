# 动态模型推荐与原生调度

## 每次任务的推荐

先取得宿主实际工具参数、可用模型及各自支持的推理强度。不能把订阅宣传、全局默认配置或这份文档当作当前账户可用性证明。

主 Agent 根据需求复杂度、跨模块依赖、架构不确定性、变更风险、上下文规模、可验证性，以及用户明确的成本和时延偏好推荐本次配置。解释每角色为何需要该能力；所有角色一律最高强度也不是动态推荐。没有成本偏好就不虚构预算或价格。

推荐表包含阶段、具体模型、推理强度、上下文范围和理由：

- 总控与需求：当前会话实际配置，保留讨论；不能用修改技能元数据宣称已切换主会话。
- 设计与拆分：设计角色。
- 实现与修复：实现角色。
- 设计审查、代码两轴审查、验收：审查角色。
- 知识维护、交付：按实际工作选择上述角色之一，写入阶段路由，可复用模型。
- 首次 Wiki 接入：尚未完成时，根据仓库研究难度推荐 Wiki Host，写入可选 `initialization.wiki_host`；与上述选择一并确认。Wiki Host 使用新上下文，可复用适合的阶段模型。单独初始化时保存其独立确认，后续仍有效就沿用。

设计、实现、审查的规范模型 ID 必须两两不同。不同强度、模型别名或三个相同模型的 Agent 不满足条件。集中确认后保存用户确认记录与配置；每阶段不再询问。需要更改配置时说明新证据和影响，确认后保存新修订，重新检查受影响产物。

## 上下文交接

所有执行角色使用新上下文。总控调用原生子 Agent 时使用 `fork_turns: "none"`，显式传入确认后的 `model` 和 `reasoning_effort`；实际参数名称以宿主工具签名为准。该参数形式依据本包创建时的宿主接口，其他接口只有提供等价能力才支持。

交接包只包含任务/阶段、输入版本、必要文件或章节指针、约束、验收条件、工具入口、输出位置和已确认决策。设计不继承完整聊天；实现不预载所有任务；审查不继承实现者思考、自评或完成判断。原始测试输出可作输入，审查者仍独立核查。换新 Agent 时交接完成事项、验证证据和未解决问题，不复制历史对话。

依任务确定阅读预算与切换条件。发现信息不足先按需检索，超过预算且尚有实质工作时保存检查点并换新 Agent；不要以压缩后继续同一线程冒充上下文隔离。

## 落实与记录

使用显式模型调用而不是让子 Agent 自行选模型。若自定义 Agent 配置覆盖请求，先核对实际生效层；不能用不符矩阵的覆盖继续执行。[官方子 Agent 配置说明](https://learn.chatgpt.com/docs/agent-configuration/subagents)

调度记录保存角色、阶段、任务、Agent ID、请求模型/强度、上下文模式与配置证据；宿主返回实际模型时一并保存并比对，没有返回就标明“请求已记录，实际值未独立回报”，不能伪造实际值。

并发数由宿主上限决定，给独立审查留额度；无独立任务时不为并行而拆分。修复使用实现角色，复审使用新审查上下文。OpenWiki host 自己串行消费队列，不继续委派页面工作。

辅助脚本校验声明的配置与能力，不探测模型账户，也不会启动 Agent。若宿主没有显式模型、显式强度、新上下文控制，或可用模型不足三种，需求探索可继续，但实质执行前报告能力阻塞；不绕开沙箱、权限或改成隐式同模型执行。
